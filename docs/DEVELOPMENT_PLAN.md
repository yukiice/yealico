## 1. 目标与范围

### 1.1 已明确的需求

1. 主要运行于 Android。
2. 应用以 React Native + TypeScript 开发，允许结合 Kotlin 原生模块。
3. 能导入并运行用户已有的 Yealico 站点规则，而不要求用户为每个站点重新编写扩展。

### 1.2 首版建议范围

先实现图片 / 漫画阅读闭环：

**导入规则 → 站点列表 → 内容列表 → 详情 / 必要的章节列表 → 图片阅读 → 保存并恢复进度。**

导入方式至少覆盖规则 JSON、规则 URL 和二维码；二维码的兼容范围由 P0 的载荷结论决定，**不能把“能扫”当作“能导入”**。

默认只选一种阅读模式作为首版验收模式，建议竖向连续阅读；横向翻页后续增加。章节、搜索、登录和分页是否进入首版，由选定的真实规则样本决定，不擅自删掉目标站点所必需的能力。

首版不承诺：

- 兼容全部 Yealico 规则或全部历史版本。
- 视频、小说、离线整本下载、云同步、规则市场、自动规则更新。
- iOS 发布、应用商店上架、绕过站点访问控制或反爬验证。
- 完整复刻 Yealico 的每一种展示布局。

**兼容性的定义：未经手工改写的目标规则，在声明支持的功能范围内得到正确结果。仅能导入 JSON 不算兼容。**

## 2. 开始前的输入与默认决策

### 2.1 向用户集中索取一次

- 3～5 份实际使用的 Yealico 规则 JSON 或导入地址，并标出最重要的站点。
- 每个站点的一个可测试详情地址及大致预期：标题、章节、图片顺序等。
- 哪些站点需要登录、JS 加载或手动浏览器验证。
- 可用的 Android 真机 / 模拟器及系统版本。
- 如方便，提供原版 Yealico 中的截图或人工确认结果。

不要索取账号密码或让用户把 Cookie 提交到仓库。需要登录时，优先由用户在设备内操作。

### 2.2 没有样本时可以先做什么

可以初始化应用、建立测试框架、制作合成 HTML/JSON fixture、设计最小规则执行链路。

不能：把自造 fixture 通过宣布为真实 Yealico 兼容；不能把未经授权的站点私自选为产品验收样本。真实兼容性验收保持“待验证”。

### 2.3 默认工程方向

- RN + TypeScript；默认优先评估 Expo development build。
- 不把 Expo Go 当作最终运行环境。
- Kotlin 仅在验证发现必要时加入；不为了目录完整而创建空壳原生模块。
- 先验证 JS 静态 HTML 解析，不预先认定必须使用 Jsoup。
- 不固定本文未验证的库版本。初始化时检查官方兼容说明，记录 RN、JS 引擎、Expo（如使用）、Android SDK、JDK 和关键依赖版本，提交锁文件。
- 若选择 Expo 生成原生工程，明确配置和本地模块的持久化方式；不要把重要改动只留在会被重新生成的文件内。

## 3. 核心技术约束

### 3.1 一套规则语义，多个底层适配器

规则核心独立于页面和平台，负责：

- 规则结构校验、版本信息和能力扫描。
- URL / 请求占位符展开、函数链、正则处理、分页计划。
- 提取规则编排、字段归一化、结构化错误和诊断。

底层适配器负责：

- 网络请求和站点会话。
- 静态 HTML / JSON 文档加载与查询。
- WebView 登录、动态页面加载以及 DOM 查询或快照。
- 存储和图片资源加载。

禁止在 Kotlin 中另写一套完整规则引擎。若增加原生解析后端，必须通过同一组语义契约测试；默认只使用一种静态解析后端，不随意在不同站点间切换。

### 3.2 加载策略必须明确

普通页面使用网络请求 + 静态解析；规则声明或已验证能力要求浏览器时使用 WebView。

不能把“结果为空”直接解释为“需要 WebView”。先区分合法空列表、选择器错误、未登录、请求错误和浏览器加载要求。若设置 fallback，必须记录触发原因并限制次数。

浏览器模式定义就绪条件、总超时、滚动上限和取消机制，不能仅靠固定 sleep。优先以渲染后的 DOM 快照复用规则逻辑；若某项行为无法由快照保留，使用受控查询适配器并补测试，不悄悄改变语义。

### 3.3 先测行为差异，再写兼容转换

不要默认 CSS、JSONPath、正则、URL 编码在不同库中完全一致。

对 `this`、`$root`、索引、属性缺失、相对地址、正则无匹配与替换、函数链顺序分别建立 fixture。选择器兼容逻辑集中管理，不散落到页面或站点业务代码中。

只实现样本或明确规范要求的函数，未知函数返回 `UNSUPPORTED_FEATURE`，不静默跳过。不要使用 `eval` 执行导入字符串；JSONPath 等表达式实现需限制可执行代码能力。

### 3.4 会话统一，敏感凭证不进入业务层

页面和规则引擎只持有站点会话标识，不传播原始 Cookie。

实现必须明确：普通请求、WebView 和图片加载如何使用正确的站点 Cookie / UA / Referer，登录变化如何同步，以及退出登录如何清理。

Cookie 按目标 URL 和有效属性处理，不能把一个域名的 Cookie 无差别发送给其他域名。跨域重定向不盲目转发凭证。不要通过通用 JS 消息接口暴露 HttpOnly Cookie。

登录信息不得进入日志、fixture、错误报告或版本库。

## 4. 模块边界与最小接口契约

模块可先放在单一应用工程中，不要求 monorepo。建议概念分层：

- `app / features`：导航、站点、列表、详情、阅读器、设置。
- `engine`：规则模型、校验、能力分析、执行计划、函数和归一化。
- `adapters`：网络、静态解析、浏览器、图片资源、存储。
- `fixtures / tests`：脱敏样本、预期结果、适配器契约与回归测试。

先完成能支持 P1 的最小接口，不把下面清单机械实现成大框架：

| 边界 | 必须考虑的契约 |
| --- | --- |
| 请求 | URL、method、headers、body、sessionId、超时、取消；响应状态、最终 URL、headers、内容和字符集解码策略 |
| 静态解析 | 文档根 / 当前节点上下文、批量查询、数组顺序、空值语义、URL 解析基址 |
| 浏览器 | sessionId、目标 URL、就绪条件、滚动策略、超时 / 取消、最终 URL、受控提取结果 |
| 图片资源 | 地址、必要请求头、会话作用域、缓存策略；界面不自行拼装凭证 |
| 存储 | 站点、规则版本 / 哈希、收藏、历史、阅读进度、schema 版本 |
| 诊断 | 执行阶段、规则字段路径、错误码、耗时、脱敏摘要 |

特别要求：

- 先在网络边界正确处理字符集，不能所有响应一律按 UTF-8 解码。
- 每次查询以“一个列表 / 一个详情”批量执行，避免为每个字段反复跨原生或 WebView 边界。
- 分页必须有最大页数、无新增内容终止、取消和顺序保持机制；去重策略不能误删有效内容。
- 规则函数链和占位符如支持嵌套、引号或转义，应按已确认语法解析，不用简单字符串切割覆盖复杂语法。

## 5. 分阶段任务与验收

执行原则：每阶段完成后报告改动、运行过的测试、未验证项及下一步。除非需要用户样本、设备操作或改变产品范围，不要求逐步等待批准；硬性验收条件未满足时，不声称已通过。

### P0：规则清点与兼容范围

任务：

- [ ] 收集并标记目标规则及来源；脱敏并确认是否允许纳入仓库。
- [ ] 收集 Yealico 规则二维码样本，记录前缀、版本、载荷长度、可解性与来源；不把“能扫”当作“能导入”。
- [ ] 对照 Yealico 官方文档与样本实际字段，整理兼容矩阵。
- [ ] 为每个样本记录功能：CSS / JSONPath、函数、占位符、分页、章节、POST、字符集、登录、JS、请求头。
- [ ] 将功能标为首版必须 / 后续 / 不支持 / 语义待确认。
- [ ] 选择第一条无需登录、结构较简单的端到端链路；若目标样本没有这种规则，用合成样本验证底座，但不得替代真实验收。

输出：兼容矩阵、样本清单、预期结果与待确认项。

验收：每项首版能力能追溯到样本或明确规范；未知行为没有被猜测性实现掩盖。

### P1：工程与最小规则执行验证

任务：

- [ ] 初始化 RN Android 工程、TypeScript、lint、单元测试和锁文件。
- [ ] 在目标 Android Hermes 运行时实际运行静态解析、JSONPath、正则和必要函数链，不仅在 Node 测试。
- [ ] 用最小 fixtures 跑通请求占位符 → 查询 → 字段处理 → 结果归一化。
- [ ] 记录目标设备、依赖版本、输入大小、重复测量方法和解析耗时；能可靠测量时记录内存。
- [ ] 对比普通页面与最大目标样本；检查是否阻塞交互、打包是否引入不必要的 Node 依赖。
- [ ] 作出静态解析选型决定；只有 JS 路线不满足明确要求时再验证原生后端。

输出：可安装运行的 Android 骨架、首组 fixture 测试、简短选型记录。

验收：Android 上能执行规则测试并得到预期结果。若仅 Node 通过，P1 不算通过。未获得设备时明确记录，其他不依赖设备的任务可继续。

### P2：规则核心与诊断

任务：

- [x] 支持粘贴 JSON 和规则 URL 导入；区分结构错误与能力不支持（领域层已完成，UI 未接）。
- [ ] QR 导入：**必须交付，延期**。识别 URL / 原始 JSON / 自有 scheme；Yealico `v2:` 若无法解码，报 `UNSUPPORTED_QR_PAYLOAD` 并提供粘贴/URL 回退。
- [x] 保留原始规则及哈希；不要通过不可逆转换丢掉未知字段（当前为简单稳定 ID，不是安全哈希）。
- [ ] 实现 P0 确定的请求构造、选择器上下文、函数链、相对 URL 与结果模型。
- [ ] 实现目标样本必需的分页 / 章节能力及终止保护。
- [ ] 输出可定位的执行错误；建立请求、解析、归一化各阶段的诊断记录。
- [ ] 在 Node 和 Android 运行时对关键正则 / 编码 / 解析样例做一致性验证。

输出：可独立测试的规则核心与最小调试页。

验收：离线 fixture 的字段、顺序、分页结果全部符合已确认预期；未知能力明确失败，不能伪装为“站点没有内容”。

### P3：最小可用阅读闭环

任务：

- [x] 站点新增、展示、删除与重复导入处理（领域层 `SiteRepository` 已完成，UI/持久化未接）。
- [x] 内容列表、页面选择、详情展示、章节图库阅读器（单页模式）。
- [x] 图片阅读：一种模式、加载状态、失败重试、受控预加载。
- [x] 使用持久化存储保存站点和进度；以稳定内容标识关联记录，不仅依赖临时图片 URL（站点用 Android SharedPreferences，进度按 `siteId + chapterKey` 落在同一份 envelope）。
- [x] 返回 / 再进入 / 应用重启后恢复进度。
- [x] 调试页展示当前规则、阶段、结果数量与脱敏错误。

输出：至少一个真实目标站点可用的 Android 开发版本。

验收：未经手工改写的目标规则完成“导入 → 阅读 → 重启恢复”；切换页面时旧请求能取消或旧结果被丢弃；失败可重试且不会串入其他站点数据。

当前进度：导入→列表→详情→章节→阅读器→调试页已在 Android 模拟器跑通；站点重启恢复已验证，**阅读进度的重启恢复仍缺真机证据**；阅读器图片未加载成功（漫画柜章节选择器漂移）。详见 [Android 验收记录](architecture/p3-android-verification.md)。

**必须功能债**：Yealico QR 导入。当前只完成识别与明确失败；相机扫码、v2 解码、站点落库 UI 未完成。详见 [P3 站点导入与二维码](architecture/p3-site-import.md)。

### P4：登录、动态页面与必要原生能力

按 P0 样本决定是否进入首版；若目标站点依赖这些能力，不得跳过。

任务：

- [ ] WebView 用户登录及手动验证入口。
- [ ] 验证 WebView、请求和图片的会话一致性与跨站隔离。
- [ ] 动态 DOM 的就绪、滚动、超时、取消和受控提取。
- [ ] 仅针对已复现的缺口增加 Kotlin 模块；记录为何已有适配器无法满足。
- [ ] 原生调用不得阻塞 UI 线程；页面销毁 / 重建时正确释放任务和 WebView。
- [ ] WebView 桥只接受限定消息、核对来源与任务标识，不向任意网页暴露通用原生执行能力。

输出：目标复杂样本的运行结果及必要原生实现。

验收：登录 → 列表 → 详情 → 图片 → 重启 → 退出登录逐项验证；超时不会无限挂起；不支持的挑战 / 环境明确提示，不能承诺“自动绕过”。

### P5：回归与交付

任务：

- [ ] 回归全部目标规则，区分引擎问题和站点 / 网络问题。
- [ ] 检查长列表、长图、多图、连续翻页、快速退出重进、弱网和图片失败。
- [ ] 检查规则重复导入、字段缺失、非法正则、畸形 HTML、未知函数和多页无新增内容。
- [ ] 验证数据升级策略或明确当前仅为不可升级的实验版本。
- [ ] 移除敏感日志，检查依赖许可证和第三方代码署名。
- [ ] 提供可安装开发 APK、构建说明、版本信息、兼容清单和已知限制。

输出：可安装版本 + 实际测试记录 + 兼容矩阵最终状态。

验收：所有“支持”声明都有对应证据；离线测试通过与在线测试通过分别记录。不以少量合成数据或一次偶然成功替代验收。

## 6. 测试组织与质量标准

### 6.1 必备测试层

1. **规则单元测试**：占位符、函数链、正则、空值、相对 URL、排序和分页。
2. **适配器契约测试**：同一输入在选定运行时 / 解析后端得到约定结果。
3. **Android 运行时测试**：验证 Node 测试无法覆盖的 Hermes、原生依赖和生命周期。
4. **在线冒烟测试**：验证真实网络、会话、图片请求和目标站点。
5. **人工阅读验收**：阅读交互、进度恢复和目标设备表现。

fixture 保存最小化的脱敏响应和人工确认结果，标明采集日期、规则哈希、预期来源。测试不得仅用当前实现生成自己的 expected 值。

### 6.2 兼容矩阵格式

| 能力 / 样本 | 首版必需 | 离线证据 | Android 证据 | 在线证据 | 状态 / 限制 |
| --- | --- | --- | --- | --- | --- |
| 样本 A：静态列表与图片 | 待样本确认 | 待补 | 待跑 | 待跑 | 未验证 |
| 样本 B：登录 / JS | 待样本确认 | 待补 | 待跑 | 待跑 | 未验证 |

状态使用：已支持 / 部分支持 / 不支持 / 待验证。不得用“实现了函数”替代行为验证。

### 6.3 性能验收

不在没有目标设备和样本时编造性能预算。P1 建立基线后，记录可接受的解析耗时、阅读交互表现和内存观察方式。至少验证：不会无限加载、不会因分页无限增长、离开页面可停止工作、预加载有上限。

## 7. 安全、维护与许可证

- 规则和远程页面均按不可信输入处理，限制响应大小、解压输出、递归 / 分页 / 滚动次数，评估正则极端输入风险。
- 网络导入与跳转限制在支持的协议；不要把远程字符串解释为本地文件或任意原生命令。
- 区分本地规则文件导入与网页访问权限，不让页面获得本地文件读取能力。
- 保存登录信息时使用适当的受保护存储，不在普通业务表中明文复制全部凭证。
- 对网络或浏览器失败提供可诊断结果，不实现访问控制绕过。
- 参考其他项目时先检查许可证。当前仓库为 MIT，不能默认所有参考代码都可直接复制并继续以 MIT 发布。
- 首版先保证运行与诊断，不引入插件市场、自动代码下发或多规则格式兼容框架。

## 8. 开发 agent 工作方式
